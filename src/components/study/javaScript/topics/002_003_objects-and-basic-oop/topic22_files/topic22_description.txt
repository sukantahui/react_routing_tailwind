1. THE REAL-WORLD HOOK & INTUITIVE ANALOGY
--------------------------------------------------------------------------------
Think about building with LEGO blocks versus trying to cross-breed a Duck and a Truck in biology. If you create a deep inheritance tree (`FlyingSwimmingWheeledVehicle`), adding a new feature forces you to rewrite the entire genetic tree. But with LEGO blocks (Composition), if a vehicle needs flying capability, you simply snap on a 'Wing Block'; if it needs swimming, you snap on a 'Propeller Block'! Favor Composition over Inheritance!

3. STEP-BY-STEP CONCEPTUAL BREAKDOWN (WHITEBOARD EXPLANATION)
--------------------------------------------------------------------------------
1. Why 'Composition over Inheritance'?
- Deep class hierarchies become rigid and fragile ('The Gorilla/Banana Problem': you wanted a banana, but you got a gorilla holding the banana and the entire jungle!).
- Composition builds objects by combining small, focused feature behaviors.

2. Object Mixins Pattern:
A function or object that provides methods that can be copied into any class prototype or object instance using `Object.assign()`.

4. GROUNDED PRACTICAL CODE EXAMPLES (PROGRESSIVE LEARNING)
--------------------------------------------------------------------------------
--- Example 1: Flexible Character Capabilities with Mixins ---
// Small focused capability mixins:
const canFly = {
  fly() { return `${this.name} takes off into the sky!`; }
};

const canCastSpells = {
  castSpell(spell) { return `${this.name} casts ${spell}!`; }
};

class GameCharacter {
  constructor(name) { this.name = name; }
}

// Compose mixins onto prototype:
Object.assign(GameCharacter.prototype, canFly, canCastSpells);

const hero = new GameCharacter('Swadeep the Mage');
console.log(hero.fly());
console.log(hero.castSpell('Fireball'));

Teacher's Note on Example 1:
Mixins compose multiple independent behaviors onto a class without rigid inheritance trees.

5. COMMON TRAPS, ROOKIE MISTAKES & SENIOR PRO BEST PRACTICES
--------------------------------------------------------------------------------
[!] Naming collisions in mixins: If two mixins define a method with the same name, the last one assigned silently overwrites the first.

[!] Overusing mixins when simple functional composition (`pipe`) is cleaner.

6. KEY TAKEAWAYS & REVISION SUMMARY
--------------------------------------------------------------------------------
• 'Favor composition over inheritance' is a fundamental software engineering maxim.
• Mixins allow sharing capabilities across unrelated classes.
• Use `Object.assign(Class.prototype, ...mixins)` for flexible multi-behavior composition.
