1. EXECUTIVE OVERVIEW & HANDSHAKE ASYMMETRY
--------------------------------------------------------------------------------
Under RFC 793, the TCP Three-Way Handshake introduces a dangerous resource allocation asymmetry:

  * THE HANDSHAKE SEQUENCE & ASYMMETRY :
    1. STEP 1 (SYN)    : Client sends SYN ➔ Server allocates ~480B TCB in SYN Backlog (SYN_RECV).
    2. STEP 2 (SYN-ACK): Server sends SYN-ACK and waits up to 75 seconds for the final ACK.
    3. STEP 3 (ACK)    : Client returns ACK ➔ Socket transitions to ESTABLISHED.
    4. THE EXPLOIT     : Attacker floods spoofed SYNs; server commits gigabytes of RAM holding
                         half-open states, while the attacker commits zero resources!

--------------------------------------------------------------------------------
2. THE RFC 4987 TCP SYN COOKIE CRYPTOGRAPHIC ARCHITECTURE
--------------------------------------------------------------------------------

A. 32-BIT INITIAL SEQUENCE NUMBER (ISN) ENCODING :
   - Bits 31-27 (5 Bits) : Timestamp epoch $t = (\text{time}() >> 6) \pmod{32}$ (advances every 64s).
   - Bits 26-24 (3 Bits) : Encoded Maximum Segment Size (MSS) index $m \in [0, 7]$.
   - Bits 23-0 (24 Bits) : Cryptographic Signature = $\text{HMAC-SHA1}(\text{4-Tuple} \parallel t \parallel \text{SecretKey}) \pmod{2^{24}}$.

B. VERIFICATION ON STEP 3 :
   - Server computes $\text{ISN} = \text{Ack} - 1$, extracts $t$ and $m$, verifies timestamp validity,
     and re-computes HMAC. Only upon a valid match does the server allocate socket memory!

C. TCP TIMESTAMPS EXTENSION (RFC 7323) :
   - Encodes Window Scale (4 bits) and SACK (1 bit) into the TCP Timestamp TSval field,
     preserving full TCP performance features during SYN flood attacks.
