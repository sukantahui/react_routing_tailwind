1. EXECUTIVE OVERVIEW & THE PROTOCOL PARADIGM SHIFT
--------------------------------------------------------------------------------
In modern network security protocols (TLS 1.3 and SSH-2), the role of the RSA algorithm 
has fundamentally shifted:

  * THE OLD MODEL (TLS 1.2 / SSH-1): RSA was used for static encryption key exchange.
    - FATAL FLAW: Lacks Perfect Forward Secrecy (PFS); vulnerable to Bleichenbacher ROBOT attacks.
  * THE MODERN MODEL (TLS 1.3 / SSH-2): RSA is restricted STRICTLY to Digital Signature Authentication!
    - Ephemeral Key Exchange is handled exclusively via Elliptic Curves (ECDHE / X25519) for guaranteed PFS.

--------------------------------------------------------------------------------

    - TLS 1.3 allows 0-RTT connection resumption for returning clients.
    - Security Rule: 0-RTT data is vulnerable to network replay attacks!
    - Enforce 0-RTT ONLY for idempotent HTTP GET requests; strictly prohibit on POST / payment APIs.

3. RSA IN SECURE SHELL (SSH-2 / RFC 4253 & RFC 8332)
--------------------------------------------------------------------------------

  * SSH HOST KEYS (/etc/ssh/ssh_host_rsa_key):
    - Server presents its public host key on TCP port 22 to prevent Man-in-the-Middle network spoofing.

  * SSH PUBLIC KEY USER AUTHENTICATION (~/.ssh/authorized_keys vs id_rsa):
    1. Client connects and asserts public key identifier (e, N).
    2. Server verifies public key exists in target user's `~/.ssh/authorized_keys`.
    3. Server generates a random challenge nonce R and session hash H.
    4. Client signs H using local private RSA key (`~/.ssh/id_rsa`) via `rsa-sha2-256`.
    5. Server verifies signature with public key and grants shell access with ZERO password transmission!

  * SIGNATURE ALGORITHM UPGRADE:
    - Legacy `ssh-rsa` (SHA-1 digest) is DISABLED by default in OpenSSH 8.8+ due to collision attacks.
    - Modern deployments enforce `rsa-sha2-256` / `rsa-sha2-512` (RFC 8332) or `ssh-ed25519`.

4. OPENSSL 3.0 PRODUCTION COMMAND-LINE TOOLKIT
--------------------------------------------------------------------------------

  1. GENERATE ENCRYPTED 3072-BIT RSA KEY:
     $ openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -aes-256-cbc -out privkey.pem

  2. GENERATE CERTIFICATE SIGNING REQUEST (CSR):
     $ openssl req -new -key privkey.pem -out request.csr -subj "/CN=api.bank.in/O=FinTech/C=IN"

  3. DIAGNOSTIC TLS 1.3 HANDSHAKE & OCSP STAPLE INSPECTION:
     $ openssl s_client -connect api.bank.in:443 -servername api.bank.in -tls1_3 -status

7. PROFESSIONAL TIPS & COMMON PITFALLS
--------------------------------------------------------------------------------

* PROFESSIONAL PROTOCOL IMPLEMENTATION HABITS:
  1. Enforce TLS 1.3: Strictly ban static RSA key exchange in favor of ECDHE + RSA-PSS.
  2. Disable Legacy ssh-rsa (SHA-1): Upgrade OpenSSH to `rsa-sha2-256` or `ssh-ed25519`.
  3. Deploy SSH Bastion Hosts: Never expose internal database SSH ports directly to the public internet.
  4. Restrict 0-RTT Early Data: Enforce 0-RTT only on idempotent HTTP GET requests.

* COMMON BEGINNER PROTOCOL PITFALLS:
  - Using TLS 1.2 static RSA in modern deployments (Lacks forward secrecy).
  - Leaving orphaned public keys in `~/.ssh/authorized_keys` (Creates permanent backdoors).
  - Enabling 0-RTT on financial POST APIs (Vulnerable to transaction replay fraud).
  - Exposing private SSH keys (`id_rsa`) without strong passphrases.
