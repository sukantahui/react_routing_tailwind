1. EXECUTIVE OVERVIEW & THE ASYMMETRIC VS SYMMETRIC PARADOX
--------------------------------------------------------------------------------
Symmetric ciphers (AES-256-GCM) provide blazing hardware throughput (>8.4 GB/s) and quantum 
resistance, but suffer from the Key Distribution Problem. Asymmetric ciphers (RSA-2048) 
solve key distribution through public/private key pairs, but are ~1,000x slower (~3.2 MB/s) 
and cannot encrypt payloads exceeding modulus size.

A Hybrid Cryptosystem combines both primitives:
  * KEM (Key Encapsulation Mechanism) : RSA-OAEP wraps a 32-byte ephemeral AES key.
  * DEM (Data Encapsulation Mechanism): AES-256-GCM encrypts multi-gigabyte payloads at line speed.

--------------------------------------------------------------------------------
2. THE 5-STEP HYBRID CRYPTOGRAPHIC LIFECYCLE
--------------------------------------------------------------------------------

  * SENDER OPERATIONS:
    1. Ephemeral Keygen : K_session = CSPRNG( 256 bits )
    2. DEM Encryption   : (C_data, Tag, IV) = AES_256_GCM_Encrypt( Bulk_Payload, K_session )
    3. KEM Wrapping     : C_key = RSA_OAEP_Encrypt( K_session, Recipient_PublicKey )
    4. Envelope Packing : Transmit [ C_key || IV || C_data || Tag ] across untrusted network.

  * RECIPIENT OPERATIONS:
    5. Decapsulation    : K_session = RSA_OAEP_Decrypt( C_key, Recipient_PrivateKey )
                          Bulk_Payload = AES_256_GCM_Decrypt( C_data, K_session, Tag, IV )
                          (Authenticated plaintext restored with zero loss and 100% integrity!)

4. CLOUD ENVELOPE ENCRYPTION ARCHITECTURE
--------------------------------------------------------------------------------

  * KEY ENCRYPTION KEY (KEK) & DATA ENCRYPTION KEY (DEK):
    - KEK: Master RSA-4096 / ECC Key stored permanently inside FIPS 140-3 HSM.
    - DEK: Local ephemeral AES-256 key generated per database row / S3 object.

  * KEY RE-WRAPPING (INSTANT MASTER KEY ROTATION):
    - To rotate master keys on a 100 Terabyte database: Decrypt 32-byte DEK with old KEK and 
      re-encrypt with new KEK (Takes 2.1 ms, processing only 32 bytes without touching 100 TB data!).

  * CRYPTOGRAPHIC ERASURE:
    - Deleting master KEK inside HSM instantly shreds petabytes of cloud ciphertext under DPDP Act.

--------------------------------------------------------------------------------
5. OPENPGP MULTI-RECIPIENT HYBRID ARCHITECTURE
--------------------------------------------------------------------------------

When sending an encrypted document to multiple recipients (e.g. Alice, Bob, Charlie):
  - Encrypt payload ONCE with a single ephemeral AES-256 session key K.
  - Encrypt K once for Alice (RSA_Alice), once for Bob (RSA_Bob), and once for Charlie (RSA_Charlie).
  - Package: [ C_k_Alice || C_k_Bob || C_k_Charlie || C_data_AES || Tag ].

8. PROFESSIONAL TIPS & COMMON PITFALLS
--------------------------------------------------------------------------------

* PROFESSIONAL HYBRID DESIGN HABITS:
  1. Always Use AES-GCM (AEAD): Built-in 128-bit authentication tags eliminate padding oracle attacks.
  2. Generate Unique Ephemeral Keys: Never re-use symmetric session keys across multiple messages.
  3. Enforce RSA-OAEP for KEM: Never use unpadded Textbook RSA to encapsulate session keys.
  4. Secure Key De-allocation: Purge plaintext session keys from RAM via `OPENSSL_cleanse()` immediately.

* COMMON BEGINNER HYBRID PITFALLS:
  - Using AES-CBC without HMAC (Vulnerable to padding oracle attacks).
  - Encrypting bulk data directly with RSA (Causes massive CPU saturation).
  - Re-using static AES session keys (Compromising one key exposes all historical archives).
  - Forgetting to transmit the IV/Nonce alongside the ciphertext.
