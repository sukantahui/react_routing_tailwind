1. EXECUTIVE OVERVIEW & THE ORM ESCAPE HATCH PROBLEM
--------------------------------------------------------------------------------
While Object-Relational Mappers (ORMs) automatically parameterize standard CRUD operations, 
they become completely vulnerable to SQL Injection when developers invoke raw SQL escape hatches 
using string concatenation:

  * THE ORM RAW ESCAPE HATCH MATRIX :
    1. PRISMA ORM         : `$queryRawUnsafe()` (VULNERABLE) vs `$queryRaw\`...\`` (TAGGED TEMPLATE - SAFE).
    2. SEQUELIZE ORM      : `Sequelize.literal("..."+input)` (VULNERABLE) vs Standard `{ where }` (SAFE).
    3. DJANGO ORM         : `RawSQL(f"...{input}")` (VULNERABLE) vs `RawSQL("... %s", (input,))` (SAFE).
    4. ENTITY FRAMEWORK   : `FromSqlRaw("..."+input)` (VULNERABLE) vs `FromSqlInterpolated($"...{input}")` (SAFE).
    5. HIBERNATE (JPQL)   : `createQuery("..."+input)` (VULNERABLE) vs `query.setParameter()` (SAFE).

5. STUDENT MINI CHECKLIST (EXAM & CAREER ESSENTIALS)
================================================================================
  [✔] Standard ORM methods parameterize queries; raw escape hatches with concatenation re-introduce SQLi.
  [✔] Prisma `$queryRaw` tagged template literal is 100% safe; `$queryRawUnsafe()` is vulnerable.

  [✔] Dynamic T-SQL stored procedures must execute via `sp_executesql` with parameter definitions.
  [✔] PL/SQL dynamic queries must bind parameters out-of-band using the `USING` clause.
