1. WHAT IS THE IN OPERATOR?
--------------------------------------------------------------------------------
The `IN` operator determines whether a specified value matches any element in a discrete literal
list or dynamic subquery result set. It is clean, readable shorthand for multiple `OR` conditions.

A. BASIC SYNTAX (DISCRETE LIST):
   SELECT column_1, column_2
   FROM table_name
   WHERE target_column IN (value_1, value_2, value_3);

B. EQUIVALENCE TO OR:
   `WHERE city IN ('Barrackpore', 'Kolkata', 'Ichapur')`
   is logically identical to:
   `WHERE city = 'Barrackpore' OR city = 'Kolkata' OR city = 'Ichapur'`
   However, MySQL optimizes `IN (...)` by sorting the constant list and using binary search!

C. THE NOT IN OPERATOR:
   `WHERE city NOT IN ('Kolkata', 'Jadavpur')`
   is logically identical to:
   `WHERE city <> 'Kolkata' AND city <> 'Jadavpur'`


2. THE NOT IN WITH NULL TRAP (CRITICAL PRODUCTION GOTCHA!)
--------------------------------------------------------------------------------
If a list or subquery contains even a single `NULL` value, `NOT IN` ALWAYS evaluates to
`UNKNOWN` (or FALSE) for ALL candidate rows, silently returning 0 rows!

WHY DOES THIS HAPPEN?
`val NOT IN (1, 2, NULL)` expands to:
`val <> 1 AND val <> 2 AND val <> NULL`
Since `val <> NULL` is `UNKNOWN`, the entire `AND` chain evaluates to `UNKNOWN`.

THE BULLETPROOF FIX:
1. Ensure candidate columns/subqueries filter out NULLs:
   `WHERE val NOT IN (SELECT id FROM t WHERE id IS NOT NULL)`
2. Use `NOT EXISTS` instead of `NOT IN` for subqueries:
   `WHERE NOT EXISTS (SELECT 1 FROM parent_t WHERE parent_t.id = child_t.id)`


3. ROW CONSTRUCTOR (TUPLE) IN OPERATORS IN MYSQL
--------------------------------------------------------------------------------
MySQL supports composite multi-column `IN` list matching:
SELECT * FROM course_enrollments
WHERE (student_id, course_id) IN ((101, 501), (102, 502), (103, 503));
This performs composite tuple matching in a single, high-performance query.


4. SUBQUERY OPTIMIZATIONS WITH IN (SEMI-JOIN & MATERIALIZATION)
--------------------------------------------------------------------------------
In modern MySQL (8.0+), the optimizer transforms `WHERE id IN (SELECT id FROM ...)` into
an internal *Semi-Join* or *Materialized Temporary Table* with a hash index, making subquery IN
filters execute in milliseconds.


5. REAL-WORLD CASE STUDIES (BARRACKPORE & KOLKATA)
--------------------------------------------------------------------------------
CASE 1: Mamata Filtering Students from Greater Kolkata Metropolitan Regions
SELECT
    roll_no,
    CONCAT(first_name, ' ', last_name) AS student_name,
    city,
    admission_fee AS "Tuition (₹)"
FROM students
WHERE city IN ('Barrackpore', 'Kolkata', 'Ichapur', 'Jadavpur')
ORDER BY city, first_name;

CASE 2: Debangshu Finding Un-purchased Catalog Products in Kolkata Warehouse
SELECT
    product_id,
    product_name,
    stock_quantity,
    unit_price AS "Price (₹)"
FROM products p
WHERE NOT EXISTS (
    SELECT 1 FROM order_items oi WHERE oi.product_id = p.product_id
);


6. COMMON PITFALLS & DANGER ZONES
--------------------------------------------------------------------------------
1. The `NOT IN` with `NULL` Zero-Row Catastrophe.
2. Passing Massive Lists (Over 10,000 items in `IN (...)`):
   - Causes query packet bloat and memory pressure. Use a temporary staging table with a JOIN instead.
3. Forgetting Quotes around String Elements in List:
   - `WHERE city IN (Barrackpore, Kolkata)` throws syntax errors. Must be `'Barrackpore', 'Kolkata'`.


7. BEST PRACTICES & SUMMARY CHECKLIST
--------------------------------------------------------------------------------
[x] Use `IN (...)` to replace lengthy, unreadable chains of `OR` conditions.
[x] Always use `NOT EXISTS` rather than `NOT IN` when comparing against subqueries with nullable foreign keys.
[x] Index the target column to enable MySQL B-Tree index lookup optimizations.
[x] Leverage tuple matching `(col1, col2) IN ((v1, v2), ...)` for composite keys.
[x] Batch large dynamic lists using temporary tables rather than gigantic thousands-item IN strings.
