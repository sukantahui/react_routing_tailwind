1. WHAT IS THE ORDER BY CLAUSE?
--------------------------------------------------------------------------------
Relational tables are unordered mathematical sets. Without an explicit `ORDER BY` clause,
the database server guarantees NO specific sequence in the returned result set!
The `ORDER BY` clause sorts rows based on one or more columns or expressions.

A. BASIC SYNTAX:
   SELECT column_1, column_2
   FROM table_name
   ORDER BY sort_column [ASC | DESC];

B. ASCENDING (ASC) VS DESCENDING (DESC):
• `ASC` (Default): Lowest to highest (0 -> 9, A -> Z, oldest date -> newest date).
• `DESC`: Highest to lowest (9 -> 0, Z -> A, newest date -> oldest date).


2. MULTI-COLUMN (HIERARCHICAL) SORTING
--------------------------------------------------------------------------------
When multiple columns are specified, MySQL sorts primarily by the first column, and uses
subsequent columns to break ties (secondary sort):
SELECT first_name, city, admission_fee
FROM students
ORDER BY city ASC, admission_fee DESC;
-- Groups students alphabetically by city; within each city, sorts by highest fee first.


3. SORTING BY EXPRESSIONS, FUNCTIONS, AND COLUMN ALIASES
--------------------------------------------------------------------------------
Because `ORDER BY` executes AFTER the `SELECT` projection in the logical query pipeline,
you CAN safely sort by:
A. COLUMN ALIASES:
   `SELECT admission_fee * 1.18 AS total_due FROM students ORDER BY total_due DESC;`
B. CALCULATED EXPRESSIONS:
   `SELECT * FROM students ORDER BY LENGTH(first_name) DESC;`
C. CUSTOM ORDERING VIA FIELD():
   `ORDER BY FIELD(status, 'urgent', 'high', 'medium', 'low');`


4. HOW INNODB EXECUTES ORDER BY (INDEXED VS FILESORT)
--------------------------------------------------------------------------------
A. INDEXED SORT (O(1) OVERHEAD - ZERO CPU COST):
   If the `ORDER BY` columns match the leading columns of a B-Tree index in matching direction,
   InnoDB reads index leaf pages in pre-sorted order without sorting in RAM!
   In `EXPLAIN`, Extra shows NO filesort.

B. FILESORT (IN-MEMORY / DISK TEMPORARY BUFFER):
   If no matching index exists, MySQL reads candidate rows into a `sort_buffer_size` memory buffer
   and performs an in-memory quicksort or external merge sort on disk.
   In `EXPLAIN`, Extra shows `Using filesort`.


5. REAL-WORLD CASE STUDIES (BARRACKPORE & KOLKATA)
--------------------------------------------------------------------------------
CASE 1: Mamata Generating Merit-Ranked Roster in Barrackpore College
SELECT
    roll_no,
    CONCAT(first_name, ' ', last_name) AS student_name,
    admission_fee AS "Fee (₹)",
    gpa AS "Academic Score"
FROM students
ORDER BY gpa DESC, admission_fee ASC;

CASE 2: Debangshu Sorting E-Commerce Product Catalog in Kolkata
SELECT
    product_name,
    unit_price AS "Price (₹)",
    stock_quantity,
    created_at
FROM products
ORDER BY is_featured DESC, created_at DESC;


6. COMMON PITFALLS & DANGER ZONES
--------------------------------------------------------------------------------
1. Relying on Physical Insert Order:
   - Assuming un-ordered queries will return records in the order they were inserted.
2. Positional Sorting Anti-Pattern:
   - Writing `ORDER BY 1, 2` (referencing column index numbers). If `SELECT` columns are reordered, sorting silently breaks.
3. Sorting on Unindexed Columns with Large Datasets:
   - Triggers heavy `Using filesort` disk thrashing.


7. BEST PRACTICES & SUMMARY CHECKLIST
--------------------------------------------------------------------------------
[x] Always explicitly define `ORDER BY` when row sequence matters for UI rendering.
[x] Create composite indexes matching the `ORDER BY (col1, col2)` sequence to eliminate `filesort`.
[x] Use explicit column names or aliases rather than numeric positions (`ORDER BY 1, 2`).
[x] Leverage `FIELD()` for non-alphabetical custom business priority sequences.
[x] Always specify `DESC` explicitly on each column when multi-column descending sorts are needed.
