1. STEP 7 OF THE ER-TO-RELATIONAL MAPPING ALGORITHM
--------------------------------------------------------------------------------
Step 7 addresses the mapping of Extended ER (EER) Specialization and Generalization hierarchies
into physical relational tables. There are FOUR distinct architectural strategies (Option A, B, C, D),
each with distinct trade-offs in normalization, query performance, and storage overhead.

THE FOUR ARCHITECTURAL STRATEGIES:

STRATEGY 7A: MULTIPLE RELATIONS (TABLE-PER-TYPE / JOINED INHERITANCE)
• Create a table for the Superclass $C$, and create a separate table for each Subclass $S_i$.
• Subclass tables inherit the Superclass Primary Key as their own PK and FK.
• APPLICABILITY: Works for ALL specialization types (Disjoint 'd', Overlapping 'o', Total, Partial).
• ADVANTAGE: 100% 3NF normalized, zero NULL columns.
• DISADVANTAGE: Requires SQL `JOIN` operations to query subclass profiles.

STRATEGY 7B: MULTIPLE RELATIONS (TABLE-PER-CONCRETE-CLASS / SUBCLASSES ONLY)
• Create tables ONLY for the leaf subclasses $S_i$ (NO superclass table).
• Each subclass table duplicates all inherited superclass attributes.
• APPLICABILITY: Disjoint + Total specialization ONLY.
• ADVANTAGE: Fast single-table queries on specific subclasses (no joins).
• DISADVANTAGE: Redundant schema definitions; polymorphic queries across all subclasses require expensive `UNION ALL`.

STRATEGY 7C: SINGLE RELATION (TABLE-PER-HIERARCHY / SINGLE TYPE DISCRIMINATOR)
• Collapse the entire superclass and all subclasses into a SINGLE unified table.
• Include a single `type_code` / `role` ENUM column as a discriminator.
• APPLICABILITY: Disjoint specialization ONLY (Disjoint Total or Disjoint Partial).
• ADVANTAGE: Blazing-fast read/write queries without any JOINs.
• DISADVANTAGE: Subclass-specific columns will contain NULLs for non-applicable rows.

STRATEGY 7D: SINGLE RELATION (TABLE-PER-HIERARCHY / MULTIPLE BOOLEAN FLAGS)
• Collapse the entire hierarchy into a SINGLE unified table with multiple boolean flag columns
  (`is_student BOOLEAN`, `is_faculty BOOLEAN`).
• APPLICABILITY: Overlapping specialization ONLY (Overlapping Total or Overlapping Partial).
• ADVANTAGE: Fast queries for overlapping entities without multi-table joins.
• DISADVANTAGE: Wastes storage on NULL columns for non-applicable subclass fields.


2. COMPARISON MATRIX OF THE 4 STRATEGIES
--------------------------------------------------------------------------------
STRATEGY         TABLES CREATED        DISJOINTNESS     COMPLETENESS     NULL COLUMNS?   JOINS NEEDED?
--------------------------------------------------------------------------------
7A (TPT)         Super + Subclasses    d or o           Total or Partial Zero NULLs      Yes (INNER JOIN)
7B (TPC)         Subclasses Only       d ONLY           Total ONLY       Zero NULLs      No (UNION for all)
7C (TPH Single)  1 Single Table        d ONLY           Total or Partial Yes (Nullable)  No
7D (TPH Multi)   1 Single Table        o ONLY           Total or Partial Yes (Nullable)  No
--------------------------------------------------------------------------------


3. REAL-WORLD CASE STUDIES (BARRACKPORE & KOLKATA)
--------------------------------------------------------------------------------
CASE 1: Strategy 7A Table-Per-Type (Mamata's Academy Clean Normalization)
CREATE TABLE persons (
    person_id INT AUTO_INCREMENT PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL
) ENGINE=InnoDB;

CREATE TABLE students (
    person_id INT PRIMARY KEY,
    tuition_fee DECIMAL(10, 2) NOT NULL,
    CONSTRAINT fk_stud_person FOREIGN KEY (person_id) REFERENCES persons(person_id) ON DELETE CASCADE
) ENGINE=InnoDB;

CREATE TABLE faculty (
    person_id INT PRIMARY KEY,
    monthly_salary DECIMAL(10, 2) NOT NULL,
    CONSTRAINT fk_fac_person FOREIGN KEY (person_id) REFERENCES persons(person_id) ON DELETE CASCADE
) ENGINE=InnoDB;

CASE 2: Strategy 7C Single Table Inheritance (Debangshu's High-Speed Kolkata Web App)
CREATE TABLE academy_members (
    member_id INT AUTO_INCREMENT PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    member_type ENUM('Student', 'Faculty') NOT NULL,
    tuition_fee DECIMAL(10, 2) NULL, -- Only populated if Student
    monthly_salary DECIMAL(10, 2) NULL -- Only populated if Faculty
) ENGINE=InnoDB;


4. COMMON PITFALLS & DANGER ZONES
--------------------------------------------------------------------------------
1. Using Strategy 7C for Overlapping Subtypes:
   - A single ENUM column prevents an individual from being both a student and faculty! Use Strategy 7D or 7A.
2. Using Strategy 7B for Partial Specialization:
   - If an entity belongs to neither subclass, it cannot be stored anywhere!
3. Forgetting `ON DELETE CASCADE` in Strategy 7A:
   - Deleting a person leaves orphaned student or faculty rows.


5. BEST PRACTICES & SUMMARY CHECKLIST
--------------------------------------------------------------------------------
[x] Use Strategy 7A (Table-Per-Type) for clean 3NF database designs with zero NULLs.
[x] Use Strategy 7C (Table-Per-Hierarchy Single ENUM) when sub-tables have very few specific columns and query speed is paramount.
[x] Use Strategy 7D (Multiple Booleans) for overlapping specializations collapsed into a single table.
[x] Never use Strategy 7B unless the hierarchy is strictly Disjoint and Total.
