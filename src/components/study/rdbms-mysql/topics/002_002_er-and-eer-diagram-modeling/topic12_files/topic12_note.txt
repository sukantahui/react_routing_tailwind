1. WHAT IS AGGREGATION IN ER MODELING?
--------------------------------------------------------------------------------
In standard Peter Chen ER modeling, a fundamental limitation exists:
• RELATIONSHIPS CAN ONLY CONNECT ENTITIES TO ENTITIES.
• A relationship CANNOT connect directly to another relationship!

WHAT HAPPENS WHEN A RELATIONSHIP MUST RELATE TO ANOTHER ENTITY?
• Example: `Employee` works on a `Project` (Relationship: `Works_On`).
  Now, a `Manager` monitors or evaluates that specific employee working on that specific project.
• We need to treat the entire relationship `[Employee] ──< Works_On >── [Project]` as a SINGLE
  HIGHER-LEVEL COMPOSITE ENTITY so it can participate in a new relationship (`Monitors`) with `Manager`!
• This abstraction is called AGGREGATION in ER modeling.

NOTATION IN PETER CHEN ER:
• Enclosing the participating entities (`Employee`, `Project`) and their relationship (`Works_On`)
  inside a LARGE BOUNDING RECTANGLE.
• The new relationship (`Monitors`) connects the Bounding Rectangle to the outer entity (`Manager`).


2. AGGREGATION VS TERNARY RELATIONSHIPS
--------------------------------------------------------------------------------
CRITICAL ARCHITECTURAL DISTINCTION:
• A Ternary Relationship connects 3 entities simultaneously in a SINGLE atomic event
  (all 3 entities participate at the exact same moment).
• Aggregation models a TWO-TIER TEMPORAL / LOGICAL PROCESS:
  1) Tier 1: An association is first established between Entity A and Entity B (e.g. Employee assigned to Project).
  2) Tier 2: At a later time, Entity C interacts with that PRE-EXISTING association (e.g. Manager monitors that assignment).


3. RELATIONAL SCHEMA MAPPING ALGORITHM FOR AGGREGATION
--------------------------------------------------------------------------------
STEP 1: Create a table for the aggregated relationship (Tier 1):
        `employee_projects(emp_id, project_id, assigned_date, PRIMARY KEY(emp_id, project_id))`
STEP 2: Create a table for the higher-level monitoring relationship (Tier 2):
        `project_supervisions(emp_id, project_id, manager_id, evaluation_date)`
        Where `(emp_id, project_id)` is a COMPOSITE FOREIGN KEY referencing `employee_projects`!


4. REAL-WORLD CASE STUDIES (BARRACKPORE & KOLKATA)
--------------------------------------------------------------------------------
CASE 1: Mamata's Barrackpore Academy Course Mentorship Aggregation
-- Tier 1: Aggregated Relationship (Student Enrolls in Course)
CREATE TABLE student_enrollments (
    student_id INT NOT NULL,
    course_id INT NOT NULL,
    enrolled_at DATE NOT NULL DEFAULT (CURRENT_DATE),
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES students(student_id) ON DELETE CASCADE,
    FOREIGN KEY (course_id) REFERENCES courses(course_id) ON DELETE CASCADE
) ENGINE=InnoDB;

-- Tier 2: Higher-Level Relationship (Faculty Mentors Specific Enrollment)
CREATE TABLE enrollment_mentors (
    student_id INT NOT NULL,
    course_id INT NOT NULL,
    faculty_id INT NOT NULL,
    assigned_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (student_id, course_id, faculty_id),
    -- Composite FK referencing the Aggregated Tier 1 Table!
    CONSTRAINT fk_mentor_enrollment FOREIGN KEY (student_id, course_id)
        REFERENCES student_enrollments(student_id, course_id) ON DELETE CASCADE,
    CONSTRAINT fk_mentor_faculty FOREIGN KEY (faculty_id)
        REFERENCES faculty(faculty_id) ON DELETE CASCADE
) ENGINE=InnoDB;


5. COMMON PITFALLS & DANGER ZONES
--------------------------------------------------------------------------------
1. Forcing Aggregation into an Unnatural Ternary:
   - Modeling as a ternary relationship means a mentor MUST be assigned at the exact instant a student enrolls, preventing delayed or optional mentorship.
2. Missing Composite Foreign Key Link:
   - Pointing foreign keys directly to `students` and `courses` separately instead of referencing the composite `(student_id, course_id)` key of `student_enrollments`.
3. Forgetting Cascading Cleanup:
   - If a student unenrolls from a course, their mentorship record must be cleaned up via `ON DELETE CASCADE`.


6. BEST PRACTICES & SUMMARY CHECKLIST
--------------------------------------------------------------------------------
[x] Use Aggregation when an entity interacts with an established relationship.
[x] Enclose the aggregated entity-relationship cluster in a large bounding rectangle in ER.
[x] Map Tier 1 to a bridge table with a composite primary key `(A_id, B_id)`.
[x] Map Tier 2 to a higher-level table using a COMPOSITE FOREIGN KEY `(A_id, B_id)` referencing Tier 1.
[x] Configure `ON DELETE CASCADE` to guarantee referential cleanup when the base association ends.
