1. STEP 6 OF THE ER-TO-RELATIONAL MAPPING ALGORITHM
--------------------------------------------------------------------------------
In conceptual ER modeling, a Multi-Valued Attribute represents a set of zero, one, or multiple
values for a single entity instance (e.g. `{phone_numbers}`, `{hobbies}`, `{degrees}`, `{locations}`).

Because relational databases strictly enforce First Normal Form (1NF) — where every column value
must be atomic (scalar) — a multi-valued attribute CANNOT be stored as a comma-separated string or array
inside the entity's base table.

FORMAL RULE FOR STEP 6:
• For each Multi-Valued Attribute $A$ of entity type $E$:
  1) Create a new dedicated relation (table) $R_A$.
  2) Include the PRIMARY KEY of $E$ as a FOREIGN KEY attribute in $R_A$.
  3) Include the attribute $A$ itself as a column in $R_A$.
  4) The PRIMARY KEY of $R_A$ is the COMPOSITE KEY:
     $PK(R_A) = \{ PK(E), A \}$.
  5) If the multi-valued attribute is composite (e.g. `{Degree(title, university, year)}`),
     include all simple components in $R_A$ and form a composite primary key.
  6) Configure `ON DELETE CASCADE` so deleting the parent entity removes all its multi-valued items.


2. THE 1NF NORMALIZATION ADVANTAGE
--------------------------------------------------------------------------------
ANTI-PATTERN (COMMA-SEPARATED STRING):
`Student(student_id: 101, phones: "9830012345, 9830098765, 9830055555")`
• Violates 1NF atomicity.
• Cannot index individual phone numbers.
• Cannot enforce uniqueness per phone number across all students.
• Requires inefficient `LIKE '%9830012345%'` string parsing.

NORMALIZED STEP 6 TABLE (1NF & 3NF COMPLIANT):
`student_phones(student_id: 101, phone_number: "9830012345", phone_type: "Mobile")`
`student_phones(student_id: 101, phone_number: "9830098765", phone_type: "WhatsApp")`
• 100% 1NF compliant.
• Instant B-Tree search by phone number: `WHERE phone_number = '9830012345'`.
• Automatic duplicate phone prevention via Composite Primary Key.


3. REAL-WORLD CASE STUDIES (BARRACKPORE & KOLKATA)
--------------------------------------------------------------------------------
CASE 1: Mamata's Barrackpore Academy Student Phone Numbers
CREATE TABLE student_phones (
    student_id INT NOT NULL,
    phone_number VARCHAR(15) NOT NULL,
    phone_type ENUM('Mobile', 'Home', 'WhatsApp', 'Emergency') NOT NULL DEFAULT 'Mobile',
    PRIMARY KEY (student_id, phone_number),
    CONSTRAINT fk_phone_student FOREIGN KEY (student_id)
        REFERENCES students(student_id) ON DELETE CASCADE
) ENGINE=InnoDB;

CASE 2: Debangshu's Kolkata Tech Enterprise Multi-Valued Degrees
CREATE TABLE employee_qualifications (
    emp_id INT NOT NULL,
    degree_title VARCHAR(50) NOT NULL,
    institution VARCHAR(100) NOT NULL,
    passing_year INT NOT NULL,
    PRIMARY KEY (emp_id, degree_title),
    CONSTRAINT fk_qual_emp FOREIGN KEY (emp_id)
        REFERENCES employees(emp_id) ON DELETE CASCADE
) ENGINE=InnoDB;


4. QUERYING MULTI-VALUED TABLES IN SQL
--------------------------------------------------------------------------------
A. AGGREGATING PHONES INTO A FORMATTED STRING FOR UI DISPLAY:
SELECT
    s.student_id,
    s.first_name,
    s.last_name,
    GROUP_CONCAT(CONCAT(p.phone_type, ': ', p.phone_number) ORDER BY p.phone_type SEPARATOR ', ') AS all_phones
FROM students s
LEFT JOIN student_phones p ON s.student_id = p.student_id
GROUP BY s.student_id, s.first_name, s.last_name;

B. FINDING STUDENTS BY ANY REGISTERED PHONE NUMBER:
SELECT s.student_id, s.first_name, s.last_name
FROM students s
JOIN student_phones p ON s.student_id = p.student_id
WHERE p.phone_number = '9830012345';


5. COMMON PITFALLS & DANGER ZONES
--------------------------------------------------------------------------------
1. Using Comma-Separated VARCHAR:
   - Violates 1NF; prevents B-Tree indexing and foreign key validation.
2. Forgetting Composite Primary Key:
   - Defining only `student_id` as the PK allows only ONE phone per student!
3. Omitting `ON DELETE CASCADE`:
   - Deleting a student leaves orphan phone numbers in `student_phones`.


6. BEST PRACTICES & SUMMARY CHECKLIST
--------------------------------------------------------------------------------
[x] Create a dedicated table for every multi-valued attribute in the conceptual model.
[x] Define Composite Primary Key: `PRIMARY KEY (parent_id, attribute_value)`.
[x] Configure `ON DELETE CASCADE` to clean up child rows automatically.
[x] Add an optional `phone_type` or `category` tag to provide rich context.
[x] Use MySQL `GROUP_CONCAT()` to assemble values into clean display strings when querying.
