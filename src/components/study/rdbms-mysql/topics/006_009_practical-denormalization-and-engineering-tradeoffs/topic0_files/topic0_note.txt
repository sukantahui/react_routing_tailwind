2. THEORETICAL FOUNDATION & MATRICES
--------------------------------------------------------------------------------
- Core Concept: Relational normalization ensures that data dependencies are modeled
  strictly according to business invariants, preventing update, deletion, and insertion anomalies.
- Formal Rule: 1. Intentional Denormalization for High-Throughput Read Endpoints
- Decomposition Strategy: Maintain a strictly normalized 3NF transactional database for ACID writes, while offloading reads to Redis and OLAP replicas.

3. BEFORE-VS-AFTER SCHEMA TRANSFORMATION
--------------------------------------------------------------------------------
UNNORMALIZED / NON-COMPLIANT STATE:
E-Commerce checkout API executes 8-table joins on every single product page load, causing database CPU spikes.
Root Cause: Under extreme read pressure (10,000 reads/sec vs 5 writes/sec), controlled redundancy dramatically accelerates query latency.

NORMALIZED STATE:
Best of both worlds: zero transactional anomalies on writes, sub-millisecond query responses on reads.

4. SENIOR ARCHITECTURAL PITFALLS & BEST PRACTICES
--------------------------------------------------------------------------------
- PITFALL: Storing a pre-computed `total_amount_inr` on the parent `orders` table reduces multi-row table scans to single-row index lookups.
- BEST PRACTICE: Best of both worlds: zero transactional anomalies on writes, sub-millisecond query responses on reads.
- ACID INVARIANT: Always declare explicit foreign keys with ON DELETE RESTRICT to protect transactional ledgers.
