2. THEORETICAL FOUNDATION & MATRICES
--------------------------------------------------------------------------------
- Core Concept: Relational normalization ensures that data dependencies are modeled
  strictly according to business invariants, preventing update, deletion, and insertion anomalies.
- Formal Rule: 1. Multivalued Dependencies (MVD: X ->> Y) Causing Cartesian Product
- Decomposition Strategy: Split into emp_skills(emp_id, skill PK) and emp_languages(emp_id, language PK).

3. BEFORE-VS-AFTER SCHEMA TRANSFORMATION
--------------------------------------------------------------------------------
UNNORMALIZED / NON-COMPLIANT STATE:
An employee has multiple independent skills and speaks multiple independent languages in a single table.
Root Cause: If Mamata has 3 skills and speaks 3 languages, the flat table forces 3 x 3 = 9 redundant rows.

NORMALIZED STATE:
Total rows reduce from 3 x 3 = 9 down to 3 + 3 = 6 rows, scaling linearly (M + N) instead of exponentially (M x N).

4. SENIOR ARCHITECTURAL PITFALLS & BEST PRACTICES
--------------------------------------------------------------------------------
- PITFALL: Independent 1:N relations stored in the same table create combinatorial row multiplication.
- BEST PRACTICE: Total rows reduce from 3 x 3 = 9 down to 3 + 3 = 6 rows, scaling linearly (M + N) instead of exponentially (M x N).
- ACID INVARIANT: Always declare explicit foreign keys with ON DELETE RESTRICT to protect transactional ledgers.
