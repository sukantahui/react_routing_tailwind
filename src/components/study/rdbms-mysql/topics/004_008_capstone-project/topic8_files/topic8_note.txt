2. CORE CONCEPTS & IMPLEMENTATION RUNBOOKS
--------------------------------------------------------------------------------
[1. EXPLAIN ANALYSIS]
EXPLAIN ANALYZE runs the query in MySQL 8.0 and outputs actual execution times, iterator costs, row counts, and loop iterations.

SQL Implementation:
-- 🔍 EVALUATING EXECUTION COSTS WITH EXPLAIN ANALYZE:
EXPLAIN ANALYZE
SELECT c.customer_id, c.full_name, COUNT(o.order_id) AS order_count
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_date >= '2026-01-01'
GROUP BY c.customer_id, c.full_name;

-- 📊 OUTPUT METRICS TO EVALUATE:
-- 1. Access Type (type): ALL (Bad - Table Scan) vs ref / range / const (Good).
-- 2. Rows examined vs rows returned.
-- 3. Actual time spent in nested loops and hash joins (in milliseconds).

Takeaways:
- Compare estimated rows against actual rows examined to detect stale statistics.
- Identify bottlenecks like full table scans (type=ALL) on large tables.
- Verify join algorithms (Nested Loop Join vs Hash Join).

--------------------------------------------------------------------------------
[2. COVERING INDEXES]
A covering index contains all columns requested by the SELECT and WHERE clauses, allowing MySQL to answer the query entirely from RAM.

SQL Implementation:
-- ⚡ CREATING A COMPOSITE COVERING INDEX:
-- Query:
SELECT customer_id, order_date, total_amount 
FROM orders 
WHERE customer_id = 4500 AND order_date >= '2026-01-01';

-- 🚀 Create composite index satisfying WHERE and SELECT columns:
CREATE INDEX idx_cust_date_amount ON orders (customer_id, order_date, total_amount);

-- 🔍 EXPLAIN Output Flag:
-- Extra: Using index (Covering Index - 0 Disk I/O Reads!)

Takeaways:
- Look for 'Using index' in the Extra column of EXPLAIN.
- Eliminates the secondary lookup step into the primary clustered B-Tree.
- Accelerates high-frequency API endpoints by 10x to 50x.

--------------------------------------------------------------------------------
[3. LEFTMOST PREFIX]
B-Tree indexes can only filter on composite columns starting from the leftmost column sequentially without skipping intermediate fields.

SQL Implementation:
-- 📏 MULTI-COLUMN INDEX: (branch_id, status, created_at)
-- ✅ Index Used:
SELECT * FROM transactions WHERE branch_id = 5;
SELECT * FROM transactions WHERE branch_id = 5 AND status = 'COMPLETED';
SELECT * FROM transactions WHERE branch_id = 5 AND status = 'COMPLETED' AND created_at >= '2026-01-01';

-- ❌ Index SKIPPED (Leftmost column missing!):
SELECT * FROM transactions WHERE status = 'COMPLETED';
SELECT * FROM transactions WHERE created_at >= '2026-01-01';

Takeaways:
- Order composite index columns from highest equality filtering to range filters.
- Place equality columns (branch_id, status) before range columns (created_at).
- Avoid duplicate single-column indexes when a composite index already covers the prefix.

4. SENIOR PITFALLS & PRODUCTION BEST PRACTICES
--------------------------------------------------------------------------------
Pitfalls to Avoid:
- Pitfall 1: Wrapping Indexed Columns in Functions: Writing WHERE YEAR(order_date) = 2026 prevents MySQL from using indexes on order_date, forcing a full table scan. (Rule: Write sargable queries: WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01'.)
- Pitfall 2: Over-Indexing Every Single Column: Creating 20 single-column indexes on a table bloats disk storage and slows down write/insert throughput significantly. (Rule: Create focused composite indexes targeted at high-frequency query workloads.)

Production Best Practices:
- Best Practice 1: Use EXPLAIN FORMAT=TREE: Inspect detailed query tree costs and iterator plans in MySQL 8.0+. (Provides human-readable insight into query engine execution paths.)
- Best Practice 2: Inspect sys.schema_unused_indexes: Query the sys schema after benchmarking to detect and remove redundant or unutilized indexes. (Keeps database memory footprint lean and maximizes write speed.)
