2. THEORETICAL FOUNDATION & MATRICES
--------------------------------------------------------------------------------
- Core Concept: Relational normalization ensures that data dependencies are modeled
  strictly according to business invariants, preventing update, deletion, and insertion anomalies.
- Formal Rule: 1. Partial Functional Dependency (X -> Y where X ⊂ Candidate Key)
- Decomposition Strategy: Split into Students (student_id PK), Courses (course_id PK), and Enrollments (student_id, course_id PK).

3. BEFORE-VS-AFTER SCHEMA TRANSFORMATION
--------------------------------------------------------------------------------
UNNORMALIZED / NON-COMPLIANT STATE:
In table enrollment(student_id, course_id, student_name, course_name, fee_inr, grade), student_name depends only on student_id.
Root Cause: Violates 2NF: All non-prime attributes must be fully functionally dependent on the ENTIRE composite candidate key.

NORMALIZED STATE:
Every non-prime column is now fully functionally dependent on its table's full primary key.

4. SENIOR ARCHITECTURAL PITFALLS & BEST PRACTICES
--------------------------------------------------------------------------------
- PITFALL: Storing course metadata in the enrollment junction table duplicates course fee across hundreds of enrolled student rows.
- BEST PRACTICE: Every non-prime column is now fully functionally dependent on its table's full primary key.
- ACID INVARIANT: Always declare explicit foreign keys with ON DELETE RESTRICT to protect transactional ledgers.

5. TEACHER'S MASTER SUMMARY - SIR SUKANTA HUI

or clever application code. Normalization provides the mathematical guarantee that
