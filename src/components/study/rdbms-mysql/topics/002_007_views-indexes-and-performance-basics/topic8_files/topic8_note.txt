1. THE B+TREE ARCHITECTURE IN INNODB
--------------------------------------------------------------------------------
MySQL InnoDB organizes all table and index data into balanced **B+Tree** structures. 
A B+Tree is a specialized, self-balancing M-way search tree optimized for disk storage.

Anatomy of an InnoDB B+Tree:
1. Root Page (Level $h$):
   - The single entry point page of the index tree.
   - Contains indexed key boundaries and child page pointers.
2. Intermediate (Branch) Pages (Levels $h-1 \dots 1$):
   - Direct the search navigation downwards to the correct child page.
   - Store only `(Key, Child Page Pointer)` pairs.
3. Leaf Pages (Level 0):
   - The bottom-most level of the tree.
   - Contains the indexed key and either the full row data (Clustered Index) 
     or the primary key value (Secondary Index).
   - **Doubly-Linked List**: All leaf pages are connected via previous/next pointers, 
     enabling ultra-fast horizontal range scans.

2. HIGH FAN-OUT & SHALLOW TREE DEPTH
--------------------------------------------------------------------------------
The number of child pointers a single 16KB index page can hold is called its **Fan-Out** ($B$).
- In a 16KB page, if each key + pointer takes 16 bytes, a single page can hold 
  approx. **1,000 child pointers** ($B \approx 1000$).

Tree Capacity by Height:
- Level 1 (Root only): Holds up to 1,000 records.
- Level 2 (Root + Leaves): Holds up to $1,000 \times 1,000 = 1,000,000$ records.
- Level 3 (Root + Branches + Leaves): Holds up to $1,000 \times 1,000 \times 1,000 = 1,000,000,000$ (1 Billion!) records.

Key Insight: Even a 1-billion row database requires only **3 to 4 page hops** to locate any key!

3. LOOKUP MECHANICS: POINT SEEK VS RANGE SCAN
--------------------------------------------------------------------------------
1. Point Lookup (Equality Search: `WHERE student_id = 45012`):
   - Binary search within the Root Page to find the appropriate child branch pointer.
   - Hop to Intermediate Branch Page → Binary search to find child leaf pointer.
   - Hop to Leaf Page → Binary search to pinpoint exact row.
   - Total Cost: 3 Page Reads ($O(\log N)$).

2. Range Scan (`WHERE fee_paid_inr BETWEEN 20000 AND 30000`):
   - Step 1: Traverse the tree from Root to Leaf to find the lower bound (20,000) in $O(\log N)$.
   - Step 2: Traverse horizontally across the **Leaf Doubly-Linked List** sequentially 
     reading records until reaching a key > 30,000.
   - Never re-traverses the root/branch pages during range traversal!

4. PAGE FILL FACTOR & PAGE SPLITS
--------------------------------------------------------------------------------
1. Sequential Inserts (e.g. `AUTO_INCREMENT` IDs):
   - InnoDB fills index pages to approx. **15/16 (93.75%)** capacity before allocating 
     a new page at the end.
   - Zero page splits; results in compact, contiguous disk storage.

2. Random Inserts (e.g. random UUIDs / Hashes):
   - When a new key must be inserted into a page that is already 100% full, InnoDB 
     must perform a **Page Split**:
     1. Allocates a new empty 16KB page.
     2. Moves ~50% of the keys from the full page to the new page.
     3. Inserts a new pointer into the parent branch page.
   - Consequence: Random inserts cause 50% storage waste (fragmentation) and 
     massive write I/O spikes.

5. PRODUCTION EXAMPLES (ACADEMY RANGE QUERIES)
--------------------------------------------------------------------------------
Example 1: High-Performance Date Range Scan
    CREATE INDEX idx_enrollment_date ON enrollments (enrollment_date);

    -- Fast B-Tree range traversal using leaf doubly-linked list:
    SELECT enrollment_id, student_id, fee_amount_inr
    FROM enrollments
    WHERE enrollment_date BETWEEN '2026-01-01' AND '2026-06-30'
    ORDER BY enrollment_date ASC;

6. SUMMARY OF BEST PRACTICES
--------------------------------------------------------------------------------
1. Prefer sequential integers (AUTO_INCREMENT or BIGINT) for primary key clustering.
2. Avoid random UUIDs as clustered primary keys to prevent constant 50% page splits.
3. Leverage B-Tree leaf doubly-linked lists for indexed `BETWEEN`, `>`, `<`, and `ORDER BY` queries.
4. Keep index key columns as narrow (compact) as possible to maximize page fan-out.
