1. WHY EXPLICITLY NAME TABLE CONSTRAINTS?
--------------------------------------------------------------------------------
In MySQL, constraints (Primary Keys, Foreign Keys, Unique Keys, and CHECK constraints)
can be declared with or without explicit names.

A. ANONYMOUS CONSTRAINTS (BAD PRACTICE):
   If you write: `FOREIGN KEY (student_id) REFERENCES students(student_id)`, MySQL generates
   an arbitrary internal symbol name such as `student_payments_ibfk_1` or `students_chk_1`.

B. EXPLICITLY NAMED CONSTRAINTS (ENTERPRISE BEST PRACTICE):
   If you write: `CONSTRAINT fk_payments_student FOREIGN KEY ...`:
   • Error messages explicitly name the violated business rule (`Check constraint 'chk_fee_floor' is violated`).
   • Database migrations can reliably drop or alter constraints using known, deterministic symbol names across Dev, Staging, and Production.
   • Schema definitions become self-documenting.


2. INDUSTRY-STANDARD CONSTRAINT NAMING CONVENTIONS
--------------------------------------------------------------------------------
PREFIX       CONSTRAINT TYPE       EXAMPLE NAMING TEMPLATE
--------------------------------------------------------------------------------
pk_          Primary Key           CONSTRAINT pk_students PRIMARY KEY (student_id)
fk_          Foreign Key           CONSTRAINT fk_payments_student FOREIGN KEY (student_id) REFERENCES ...
uq_          Unique Key            CONSTRAINT uq_students_email UNIQUE (email)
chk_         Check Constraint      CONSTRAINT chk_students_fee_floor CHECK (admission_fee >= 10000)
--------------------------------------------------------------------------------


3. SCOPE AND UNIQUENESS OF CONSTRAINT SYMBOLS
--------------------------------------------------------------------------------
1. Foreign Key Constraint Names:
   - Must be UNIQUE ACROSS THE ENTIRE DATABASE SCHEMA! (Two tables in the same database cannot have foreign keys with the same name).
2. CHECK Constraint Names:
   - Must be UNIQUE PER TABLE (and preferably unique across schema).
3. Primary Key Constraint Names:
   - In MySQL InnoDB, the Primary Key index is always internally identified as `PRIMARY`, though `CONSTRAINT pk_name PRIMARY KEY` is supported for ANSI SQL compliance.


4. REAL-WORLD CASE STUDIES (BARRACKPORE & KOLKATA)
--------------------------------------------------------------------------------
CASE 1: Mamata's Barrackpore Standardized Enterprise Schema
CREATE TABLE student_admissions (
    student_id INT AUTO_INCREMENT,
    roll_no VARCHAR(20) NOT NULL,
    email VARCHAR(100) NOT NULL,
    admission_fee DECIMAL(10, 2) NOT NULL DEFAULT 15000.00,
    city ENUM('Barrackpore', 'Kolkata', 'Ichapur', 'Jadavpur') NOT NULL,
    -- Standardized Named Constraints
    CONSTRAINT pk_student_admissions PRIMARY KEY (student_id),
    CONSTRAINT uq_student_roll UNIQUE (roll_no),
    CONSTRAINT uq_student_email UNIQUE (email),
    CONSTRAINT chk_student_fee_floor CHECK (admission_fee >= 10000.00)
) ENGINE=InnoDB;

CASE 2: Debangshu's Kolkata E-Commerce Order Linkage Schema
CREATE TABLE order_invoices (
    invoice_id BIGINT UNSIGNED AUTO_INCREMENT,
    order_id INT NOT NULL,
    customer_id INT NOT NULL,
    invoice_total DECIMAL(12, 2) NOT NULL,
    -- Named Referential Constraints
    CONSTRAINT pk_order_invoices PRIMARY KEY (invoice_id),
    CONSTRAINT fk_invoices_order FOREIGN KEY (order_id)
        REFERENCES orders(order_id) ON DELETE RESTRICT,
    CONSTRAINT fk_invoices_customer FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id) ON DELETE RESTRICT,
    CONSTRAINT chk_invoices_total CHECK (invoice_total > 0.00)
) ENGINE=InnoDB;


5. COMMON PITFALLS & DANGER ZONES
--------------------------------------------------------------------------------
1. Duplicate Foreign Key Names Across Tables:
   - Naming a foreign key `fk_student` in table A and `fk_student` in table B causes Error 1005 (Can't create table / Duplicate foreign key constraint name).
2. Forgetting Table-Level Constraint Syntax:
   - Writing `student_id INT CONSTRAINT pk_id PRIMARY KEY` is invalid inline syntax; name constraints at the table level.
3. Obscure Error Messages:
   - Debugging `ERROR 1452: constraint fails (college_ibfk_4)` takes 10x longer than `fails (fk_payments_student)`.


6. BEST PRACTICES & SUMMARY CHECKLIST
--------------------------------------------------------------------------------
[x] Always name constraints explicitly using standard prefixes (`pk_`, `fk_`, `uq_`, `chk_`).
[x] Include both child and parent table names in foreign key symbols (`fk_child_parent`).
[x] Keep foreign key symbol names unique across the entire database schema.
[x] Define named constraints at the table level at the bottom of the `CREATE TABLE` block.
[x] Use explicit symbols to write clean, deterministic `ALTER TABLE` migration scripts.
