1. WHAT IS THE AUTO_INCREMENT ATTRIBUTE?
--------------------------------------------------------------------------------
`AUTO_INCREMENT` is a column-level attribute in MySQL that automatically generates a unique,
monotonically increasing integer identifier for each newly inserted record.

CORE RULES IN MYSQL INNODB:
• A table can have at most ONE `AUTO_INCREMENT` column.
• The `AUTO_INCREMENT` column MUST be defined as an indexed key (typically the `PRIMARY KEY`).
• Must be an integer data type (`TINYINT`, `SMALLINT`, `MEDIUMINT`, `INT`, or `BIGINT`).
• Only positive numbers should be used (`UNSIGNED` is recommended).


2. HOW AUTO_INCREMENT GENERATES VALUES
--------------------------------------------------------------------------------
A. PASSING NULL OR 0:
   - `INSERT INTO students (student_id, first_name) VALUES (NULL, 'Mamata');`
   - `INSERT INTO students (student_id, first_name) VALUES (0, 'Abhronila');`
   - Result: MySQL intercepts the NULL or 0 and generates the next sequential integer (e.g. 101, 102).

B. OMITTING THE COLUMN:
   - `INSERT INTO students (first_name) VALUES ('Susmita');`
   - Result: Automatically receives the next sequential ID.

C. SUPPLYING AN EXPLICIT INTEGER:
   - `INSERT INTO students (student_id, first_name) VALUES (500, 'Debangshu');`
   - Result: Row is inserted with ID 500. The internal counter immediately jumps to 501 for future inserts!


3. RETRIEVING GENERATED IDS: `LAST_INSERT_ID()`
--------------------------------------------------------------------------------
In concurrent multi-user web applications, querying `SELECT MAX(id) FROM table` is a fatal bug
because another user's insert can occur between the two queries.
MySQL solves this with `LAST_INSERT_ID()`:
• Connection-specific and thread-safe.
• Returns the first automatically generated integer from the most recent `INSERT` in the CURRENT session.
• Immune to concurrent inserts from other clients.

MULTI-ROW INSERT BEHAVIOR:
If an insert adds 3 rows (receiving IDs 101, 102, 103), `LAST_INSERT_ID()` returns 101
(the FIRST generated ID in that batch).


4. REAL-WORLD CASE STUDIES (BARRACKPORE & KOLKATA)
--------------------------------------------------------------------------------
CASE 1: Mamata's Barrackpore Parent-Child Master-Detail Insert Pattern
-- Step 1: Insert Parent Student
INSERT INTO students (first_name, city, admission_fee)
VALUES ('Mamata Hui', 'Barrackpore', 15000.00);

-- Step 2: Retrieve thread-safe generated ID
SET @new_student_id = LAST_INSERT_ID();

-- Step 3: Insert Child Payment using captured ID
INSERT INTO student_payments (student_id, amount_paid, payment_mode)
VALUES (@new_student_id, 15000.00, 'UPI');

CASE 2: Debangshu's Kolkata High-Volume Ledger
CREATE TABLE transaction_ledger (
    transaction_id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    account_id INT NOT NULL,
    amount DECIMAL(12, 2) NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;


5. COMMON PITFALLS & DANGER ZONES
--------------------------------------------------------------------------------
1. Using `INT` Instead of `BIGINT` on Fast-Growing Tables:
   - `INT UNSIGNED` caps at 4.29 billion rows. Once exhausted, all future inserts fail with Error 1062.
2. Relying on `SELECT MAX(id)`:
   - Race condition bug in concurrent web servers. Always use `LAST_INSERT_ID()`.
3. Rollbacks Do NOT Reclaim Sequence Numbers:
   - If a transaction inserts ID 105 and is rolled back, ID 105 is permanently skipped (creating gaps). This is normal and intentional for concurrency.


6. BEST PRACTICES & SUMMARY CHECKLIST
--------------------------------------------------------------------------------
[x] Use `BIGINT UNSIGNED AUTO_INCREMENT` for high-throughput tables.
[x] Always retrieve generated keys using `LAST_INSERT_ID()`.
[x] Accept that gaps in sequence numbers are normal due to transaction rollbacks and deletions.
[x] Declare the column as `PRIMARY KEY` to maintain the InnoDB clustered index.
[x] Never rely on sequential IDs for security-sensitive public URL endpoints (use UUIDs or obfuscated tokens).
