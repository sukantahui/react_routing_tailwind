MYSQL 8.0 SERVER LOGS, MONITORING & PERFORMANCE SCHEMA
TOPIC 6: Performance Schema Architecture – Instruments, Consumers & Ring Buffers
================================================================================

1. WHAT IS THE PERFORMANCE SCHEMA?
--------------------------------------------------------------------------------
The Performance Schema is a low-overhead, in-memory diagnostic engine embedded
directly into the MySQL server. It monitors internal query execution, memory
allocations, lock contention, and disk I/O events in real-time.

Key Architectural Characteristics:
- In-Memory Non-Blocking Engine: Stored entirely in system RAM (`PERFORMANCE_SCHEMA`).
- Zero Disk I/O: Telemetry is recorded in memory ring buffers with zero disk writes.
- Microsecond Precision: Nanosecond and picosecond hardware performance counters.
- Negligible Overhead: Optimized in MySQL 8.0 to introduce <1% CPU overhead.

2. CORE PILLARS: INSTRUMENTS VS CONSUMERS
--------------------------------------------------------------------------------
A. Instruments (`setup_instruments`):
   - Code-level probe locations that measure execution timing and resource usage.
   - Examples:
     - `statement/sql/select`        : Measures SELECT query execution.
     - `wait/io/file/innodb/data`    : Measures physical InnoDB disk page reads/writes.
     - `stage/sql/Sorting result`    : Measures filesort memory and disk time.
     - `memory/innodb/buffer_pool`   : Tracks InnoDB buffer pool memory consumption.

B. Consumers (`setup_consumers`):
   - Destination tables that collect and aggregate event telemetry from instruments.
   - Examples:
     - `events_statements_current`     : Currently executing statement per thread.
     - `events_statements_history`     : Last 10 statements per thread (ring buffer).
     - `events_statements_history_long`: Last 10,000 statements globally across all threads.
     - `events_statements_summary_by_digest`: Grouped summary by normalized query template.

3. DYNAMIC RUNTIME CONFIGURATION
--------------------------------------------------------------------------------
-- 1. Enable specific wait instruments dynamically:
UPDATE performance_schema.setup_instruments 
SET ENABLED = 'YES', TIMED = 'YES' 
WHERE NAME LIKE 'wait/io/table/%';

-- 2. Enable long history consumer:
UPDATE performance_schema.setup_consumers 
SET ENABLED = 'YES' 
WHERE NAME = 'events_statements_history_long';

4. QUERYING TELEMETRY IN SQL
--------------------------------------------------------------------------------
-- Inspect top 5 most time-consuming statement digests:
SELECT 
  DIGEST_TEXT, 
  COUNT_STAR AS exec_count, 
  ROUND(SUM_TIMER_WAIT / 1000000000000, 3) AS total_latency_sec,
  ROUND(AVG_TIMER_WAIT / 1000000000000, 3) AS avg_latency_sec
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC 
LIMIT 5;

5. PRODUCTION BEST PRACTICES
--------------------------------------------------------------------------------
1. Keep Performance Schema enabled (`performance_schema = ON`) in production.
2. Enable statement and table I/O consumers for real-time latency visibility.
3. Query summary tables (`events_statements_summary_by_digest`) for continuous monitoring.
