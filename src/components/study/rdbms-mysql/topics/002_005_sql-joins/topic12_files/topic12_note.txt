1. OVERVIEW: THE TRIPLE JOIN HAZARDS
--------------------------------------------------------------------------------
Even experienced backend engineers encounter catastrophic data corruption or system outages 
due to three primary join pitfalls in relational SQL:

1. Cartesian Explosions (Missing Join Conditions).
2. Accidental Row Multiplication (1:N and M:N Fan-Out Inflating Aggregate Totals).
3. The Three-Valued Logic NULL Traps (Equality with NULL and NOT IN with NULL).


2. PITFALL 1: ACCIDENTAL ROW MULTIPLICATION (THE AGGREGATE FAN-OUT BUG)
--------------------------------------------------------------------------------
⚠️ Problem: Calculating Customer Total Order Amount AND Total Payments in a Single Multi-Table Join.

Table `customers` (1 row: Mamata)
Table `orders` (2 rows: ₹2,000 and ₹3,000)
Table `payments` (2 rows: ₹1,000 and ₹4,000)

Naive Flawed Query:
```sql
SELECT 
    c.customer_name,
    SUM(o.order_amount) AS total_orders,
    SUM(p.payment_amount) AS total_payments
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
LEFT JOIN payments p ON c.customer_id = p.customer_id
GROUP BY c.customer_id, c.customer_name;
```
What Actually Happens:
• 2 Orders × 2 Payments = 4 intermediate rows!
• `SUM(o.order_amount)` returns ₹10,000 (Expected: ₹5,000) ➔ 100% INFLATED!
• `SUM(p.payment_amount)` returns ₹10,000 (Expected: ₹5,000) ➔ 100% INFLATED!

The Fix: Pre-aggregate inside CTEs or Derived Subqueries before joining!
```sql
SELECT 
    c.customer_name,
    COALESCE(ord.total_orders, 0) AS total_orders,
    COALESCE(pay.total_payments, 0) AS total_payments
FROM customers c
LEFT JOIN (
    SELECT customer_id, SUM(order_amount) AS total_orders 
    FROM orders GROUP BY customer_id
) ord ON c.customer_id = ord.customer_id
LEFT JOIN (
    SELECT customer_id, SUM(payment_amount) AS total_payments 
    FROM payments GROUP BY customer_id
) pay ON c.customer_id = pay.customer_id;
```


3. PITFALL 2: CARTESIAN EXPLOSIONS & SERVER LOCKUPS
--------------------------------------------------------------------------------
⚠️ Problem: Omitting an `ON` clause in multi-table queries (e.g. `FROM table1, table2, table3`).
• If Table 1 has 1,000 rows, Table 2 has 2,000 rows, Table 3 has 5,000 rows:
  Total Rows = $1,000 \times 2,000 \times 5,000 = 10,000,000,000$ (10 Billion Rows!).
• Result: InnoDB Buffer Pool Thrashing, Temporary Table Disk Exhaustion, Server Freeze.

Fix: Enforce ANSI-92 explicit `JOIN ... ON` syntax and set `SQL_SAFE_UPDATES = 1` or query limits.


4. PITFALL 3: THE THREE-VALUED LOGIC NULL TRAPS
--------------------------------------------------------------------------------
1. Joining on NULLs:
   In SQL, `NULL = NULL` evaluates to `UNKNOWN` (FALSE).
   If two tables have rows where `dept_id IS NULL`, an `INNER JOIN ... ON a.dept_id = b.dept_id` 
   will NEVER match those rows.
   Fix: Use Null-Safe Equality operator (`<=>`) if you intend NULLs to match: `ON a.dept_id <=> b.dept_id`.

2. The `NOT IN` with NULL Disaster:
   `SELECT * FROM students WHERE student_id NOT IN (SELECT student_id FROM enrollments);`
   If `enrollments` contains even ONE single `NULL` student_id, the entire `NOT IN` subquery 
   evaluates to `UNKNOWN`, returning 0 rows!
   Fix: Always use `NOT EXISTS` or `LEFT JOIN ... WHERE right.id IS NULL` (Anti-Join).


5. SUMMARY CHECKLIST
--------------------------------------------------------------------------------
[x] Never join multiple 1:N child tables simultaneously without pre-aggregating in CTEs/subqueries.
[x] Watch out for aggregate fan-out inflation (`SUM` / `AVG` multiplying across Cartesian child sets).
[x] Never use legacy comma syntax (`FROM A, B`); always use explicit ANSI `JOIN ... ON`.
[x] Remember that `NULL = NULL` is FALSE; use `<=>` (Null-Safe Equality) when matching NULLs.
[x] Avoid `NOT IN` with nullable subqueries; use `NOT EXISTS` or `LEFT JOIN ... WHERE right.id IS NULL`.
