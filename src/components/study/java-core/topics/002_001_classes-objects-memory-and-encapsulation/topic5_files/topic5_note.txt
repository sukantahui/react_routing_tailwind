1. OBJECT ALIASING DEFINED:
   - When two or more reference variables on the Stack hold the identical
     Heap memory address pointing to a single object instance.
   - Syntax:
       BatchProjectAccount leadRef = new BatchProjectAccount(...);
       BatchProjectAccount coLeadRef = leadRef; // Aliasing created!

2. KEY RULES & CHARACTERISTICS:
   -----------------------------------------------------------------------------
   RULE 1: No New Object Created
           - Assignment (`b = a`) only copies the 64-bit/32-bit pointer on Stack.
           - Zero additional Heap memory is allocated.

   RULE 2: Shared Mutable State (Action at a Distance)
           - Mutating an object through `coLeadRef.recordExpense(...)` alters
             the single shared instance in Heap.
           - Reading via `leadRef.getRemainingBudget()` immediately sees the change!

   RULE 3: Reference Identity (`==`)
           - `leadRef == coLeadRef` evaluates to `true` (identical Heap addresses).
           - `System.identityHashCode(leadRef) == System.identityHashCode(coLeadRef)`.

   RULE 4: Partial Severance & GC Reachability
           - Setting `leadRef = null;` clears only that local Stack slot.
           - The object on the Heap is NOT collected as long as `coLeadRef` or
             any other active GC Root holds a valid reference.
           - Object becomes GC eligible ONLY when ALL reference paths are severed.
   -----------------------------------------------------------------------------

3. DEFENSIVE STRATEGIES AGAINST UNINTENDED ALIASING BUGS:
   a) Immutability: Make fields `final` and provide no mutators (e.g. String, Record).
   b) Defensive Copying: Return cloned/copied instances from getters.
   c) Unmodifiable Wrappers: Return `Collections.unmodifiableList(internalList)`.

4. ALIASING IN CONCURRENCY:
   - Shared mutable objects accessed by multiple threads require synchronization.
   - Synchronizing on any alias locks the single object's intrinsic monitor lock
     in the HotSpot Mark Word.
