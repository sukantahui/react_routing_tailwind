1. INTRODUCTION TO REAL NUMBERS IN JAVA
In computational mathematics and software engineering, numbers with fractional parts are modeled using floating-point representations. Java provides two fundamental primitive types for floating-point values:
1. `float` (Single-precision 32-bit IEEE 754)
2. `double` (Double-precision 64-bit IEEE 754)

Both types strictly follow the international IEEE 754 standard for binary floating-point arithmetic.

2. LITERAL DECLARATIONS & SUFFIX RULES
In Java lexical grammar:
- Every numeric literal containing a decimal point (e.g. 0.5, 3.14159, 12500.0) is classified by default as a 64-bit `double` literal.
- Assigning a default double literal to a 32-bit `float` variable results in a compile-time type mismatch error because converting an 8-byte double to a 4-byte float is a narrowing conversion that could cause loss of magnitude or precision.

Examples:
  float radius = 7.5;      // COMPILE ERROR: cannot convert from double to float
  float radius = 7.5f;     // VALID: 'f' or 'F' designates single-precision float literal
  double pi = 3.14159265;  // VALID: default double
  double tax = 18.5d;      // VALID: optional 'd' or 'D' suffix

3. IEEE 754 BINARY ARCHITECTURE
A. Float (32-bit Single Precision):
   - 1 bit Sign (0 for positive, 1 for negative)
   - 8 bits Biased Exponent (bias = 127, range -126 to +127)
   - 23 bits Significand / Mantissa (plus 1 implicit leading normalized bit = 24 effective bits)
   - Precision: ~6 to 7 significant decimal digits
   - Smallest positive subnormal: 1.4E-45
   - Smallest positive normal: 1.17549435E-38
   - Largest positive finite value: 3.4028235E38

B. Double (64-bit Double Precision):
   - 1 bit Sign
   - 11 bits Biased Exponent (bias = 1023, range -1022 to +1023)
   - 52 bits Significand / Mantissa (plus 1 implicit leading normalized bit = 53 effective bits)
   - Precision: ~15 to 17 significant decimal digits
   - Smallest positive subnormal: 4.9E-324
   - Smallest positive normal: 2.2250738585072014E-308
   - Largest positive finite value: 1.7976931348623157E308

4. THE FUNDAMENTAL BINARY FRACTION TRAP
Why does 0.1 + 0.2 == 0.3 evaluate to false?
In base 10 (decimal):
  1/10 = 0.1 (exact finite representation)
In base 2 (binary):
  Fractions are formed by sums of powers of 2 (1/2, 1/4, 1/8, 1/16, 1/32, ...).
  0.1 in binary is 0.0001100110011001100110011... (infinitely repeating).
  When truncated to 53 bits of double precision:
  0.1 is approximately 0.100000000000000005551115123126...
  0.2 is approximately 0.200000000000000011102230246252...
  0.1 + 0.2 produces 0.300000000000000044408920985006...
  0.3 is approximately 0.299999999999999988897769753748...

Because 0.30000000000000004 != 0.29999999999999998, `0.1 + 0.2 == 0.3` is false!

5. SPECIAL IEEE 754 VALUES (INFINITY AND NaN)
Unlike integer division by zero which throws ArithmeticException, floating-point arithmetic handles edge cases via IEEE 754 special values:
- Positive Infinity (`Double.POSITIVE_INFINITY`): generated by `10.0 / 0.0`
- Negative Infinity (`Double.NEGATIVE_INFINITY`): generated by `-10.0 / 0.0`
- Not-a-Number (`Double.NaN`): generated by `0.0 / 0.0` or `Math.sqrt(-4.0)`

Special Rule for NaN:
`Double.NaN == Double.NaN` evaluates to `false`.
To test for NaN, you MUST call `Double.isNaN(value)`.

6. FINANCIAL COMPUTATION BEST PRACTICES
For currency calculations (e.g. student fees at Coder & AccoTax Barrackpore in Indian Rupees ₹):
NEVER use float or double! Use `java.math.BigDecimal` instantiated with string literals:
```java
BigDecimal fee = new BigDecimal("12500.50");
BigDecimal gst = new BigDecimal("2250.09");
BigDecimal total = fee.add(gst);
```
